# 团队怎样用 Git 协作, 又怎样在 JS/TS 与 Go 仓里读懂一条调用链？

## 常见问题

- 简述 Git 的工作流
- 如何阅读大型项目的源码？

## 概念索引

- 分支模型: 约定各类分支的用途与生命周期;
- 提交: 一次可回溯、可回滚的变更单元;
- 合并: 保留两条历史并生成合并提交;
- 变基: 把一串提交搬到新的基底上;
- 发布单元: 一次打 tag 的最小制品, 一个包或一个 module;
- 调用链: 从入口追到存储的函数序列;

## Git 工作流怎么选？

| 模型 | 分支 | 适用 |
| --- | --- | --- |
| 主干开发 | 只有 main, 小步提交 | 持续部署、团队成熟 |
| GitHub Flow | main + 功能分支 + PR | 大多数 Web 项目 |
| GitFlow | main、develop、release、hotfix | 有版本发布窗口的产品 |

- 功能分支: 一个分支只做一件事, 生命周期不超过几天;
- PR: 合并前过 CI 与至少一人 review, 讨论留在 PR 里;
- 提交: 一个提交做一件完整的事, 信息写清动机而不只是改动;
- 变基: 本地分支用 rebase 整理, 公共分支只用 merge;
- 禁改: 已推送的公共历史不 rebase, 否则所有人重新对齐;
- 发布: 打 tag 标记版本, 与构建产物一一对应;

## 多栈仓怎么切发布单元？

- 工作区: pnpm 用 pnpm-workspace.yaml, Go 用 go.work 的 use 拼模块;
- 模块: 每个 go.mod 是一个发布单元, JS 每个 package.json 也是;
- 坑: go.work 官方建议不入库, CI 读它测的是本地拼装版本;

module 与 tag 规则见 [Go 模块文档](https://go.dev/ref/mod#vcs-version), 工作区语义见 [workspaces](https://go.dev/ref/mod#workspaces)。

## 阅读源码先看什么？

多栈仓先读构建入口: Makefile、Taskfile、package.json scripts、go.mod 决定怎么构建。

- 定位入口: JS 看 package.json 的 main、exports、bin, Go 看 cmd/;
- 看结构: 先读目录与 README, 判断按能力还是按层拆分;
- 跑最小用例: 写十行调用代码, 打断点走一遍真实路径;
- 跟一条链: 选一个功能从入口追到存储, 沿途记下边界;
- 读测试: 测试是行为说明书, 比注释更接近事实;
- 看历史: git log 与 blame 解释某段代码为什么长这样;
