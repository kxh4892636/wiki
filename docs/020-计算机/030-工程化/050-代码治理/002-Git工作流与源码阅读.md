# 团队怎样用 Git 协作, 又怎样快速读懂一个陌生的大型项目？

## 常见问题

- 简述 Git 的工作流
- 如何阅读大型项目的源码？
- 项目上有什么技术难点？

## 概念索引

- 分支模型: 约定各类分支的用途与生命周期;
- 提交: 一次可回溯、可回滚的变更单元;
- 合并: 保留两条历史并生成合并提交;
- 变基: 把一串提交搬到新的基底上;
- 入口: 程序开始执行的位置;
- 调用链: 从入口一路追到具体实现的函数序列;

## Git 工作流怎么选？

| 模型 | 分支 | 适用 |
| --- | --- | --- |
| 主干开发 | 只有 main, 小步提交 | 持续部署、团队成熟 |
| GitHub Flow | main + 功能分支 + PR | 大多数 Web 项目 |
| GitFlow | main、develop、release、hotfix | 有版本发布窗口的产品 |

- 功能分支: 一个分支只做一件事, 生命周期不超过几天;
- PR: 合并前过 CI 与至少一人 review, 讨论留在 PR 里;
- 提交: 一个提交做一件完整的事, 信息写清动机而不只是改动;
- 变基: 本地分支用 rebase 整理, 公共分支只用 merge;
- 禁改: 已推送的公共历史不 rebase, 否则所有人要重新对齐;
- 发布: 打 tag 标记版本, 与构建产物一一对应;

```text
主分支:  A---B---C-------M---N
功能分支:      \--d--e--/
rebase 后:  d'--e' 叠到 C 上, 再 merge 进主干
```

## 阅读源码先看什么？

- 定位入口: 看 `package.json` 的 `main`、`exports`、`bin`;
- 看结构: 先读目录与 README, 判断按能力还是按层拆分;
- 跑最小用例: 写十行调用代码, 打断点走一遍真实路径;
- 跟一条链: 选一个功能从入口追到存储, 沿途记下边界;
- 读测试: 测试是行为说明书, 比注释更接近事实;
- 看历史: `git log` 与 `blame` 解释某段代码为什么长这样;

## 怎样避免读不下去？

- 目标: 每次只回答一个具体问题, 不要试图通读全部;
- 分层: 先看接口与数据流, 细节等用到再展开;
- 画图: 把模块、依赖方向与数据流画出来, 比记忆可靠;
- 时间盒: 一小时没进展就换入口或找人问, 避免沉没成本;
- 求证: 假设要写成可运行的最小例子, 不靠猜;

## 技术难点怎么讲清楚？

- 结构: 背景与约束 → 可选方案 → 选择理由 → 结果数字;
- 数字: 用 QPS、延迟、内存、失败率说明前后差异;
- 取舍: 说清放弃了什么, 例如一致性换可用性;
- 复盘: 上线后遇到的问题与后续改进, 比方案本身更有说服力;
- 反例: 只罗列用了什么技术, 说不出约束与代价, 会被追问穿;
