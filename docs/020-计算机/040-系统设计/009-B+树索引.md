# MySQL 为什么用 B+ 树做索引？

## 常见问题

- MySQL 为什么使用 B+ 树来作索引，对比 B 树它的优点和缺点是什么？
- 数据库索引的实现原理是什么？
- B+ 树中叶子节点存储的是什么数据
- MySQL 索引使用什么数据结构？
- 数据库索引的叶子结点为什么是有序链表？

## 概念索引

- 页: InnoDB 读写磁盘的最小单位, 默认 16KB;
- 扇出: 一个非叶子节点能指向的子节点数;
- B 树: 每个节点都存数据的多路平衡树;
- B+ 树: 只在叶子存数据, 叶子再串成链表;
- 叶子链表: 让范围查询变成顺序扫描;
- 回表: 二级索引拿到主键后再查一次聚簇索引;

## 为什么以页为单位组织索引？

- 页大小: InnoDB 默认 `innodb_page_size` 为 16KB;
- 读盘: 一次 IO 至少读一页, 页内顺序访问几乎不额外花钱;
- 目标: 让一次查询只碰少数几页, 树越矮越好;
- 权衡: 页太小扇出低树变高, 页太大一次读入又浪费;
- 填充: 顺序插入时页约 15/16 满, 随机插入则在一半到 15/16 之间;

## B+ 树和 B 树差在哪？

| 项 | B 树 | B+ 树 |
| --- | --- | --- |
| 数据位置 | 每个节点都能存数据 | 只有叶子存数据或指针 |
| 非叶子内容 | 键、数据、指针 | 键与子页指针 |
| 单页扇出 | 小 | 大, 同页能指更多子节点 |
| 点查 | 可能在中间层命中 | 一定走到叶子 |
| 范围查询 | 中序回溯, 随机 IO | 沿叶子链表顺序扫 |

- 优点: 树更矮, 页访问更少, 范围与排序友好;
- 缺点: 单条点查多一次叶子页访问, 空间利用率要求更高;
- 结论: 数据库以范围扫描和排序为主, 这笔交换划算;

## 三层能放多少行？

- 假设: 主键 8 字节加页号 6 字节, 一页约存 1170 个键;
- 叶子: 每行 1KB 时一页约 16 行;
- 估算: 1170×1170×16 约 2000 万行, 只需三次页访问;
- 意义: 千万级表的主键点查仍是常数级 IO;
- 前提: 行更宽或主键更长时, 层数与 IO 都要相应增加;

## 叶子节点存的是什么数据？

- 聚簇索引: 叶子存整行数据, 主键就是数据本身;
- 二级索引: 叶子存索引列与主键值, 不存整行;
- 非叶子: 只存索引键与指向下层页的指针;
- 主键长度: 二级索引都带主键, 主键越长所有索引越大;
- 推论: 用自增短主键, 二级索引更小, 插入也更顺序;

## 叶子节点为什么是有序链表？

- 结构: 页内按键有序, 页与页之间用双向链表串起来;
- 范围: 先定位起点页, 再顺着链表读, 变成顺序 IO;
- 排序: `ORDER BY` 可直接复用索引顺序, 免掉额外排序;
- 分页: 深分页仍要跳过前面的行, 链表只省排序不省 skip;
- 代价: 随机插入会触发页分裂, 自增主键能减少分裂;

## EXPLAIN 怎么判断索引有没有用？

| 观察点 | 取值 | 判读 |
| --- | --- | --- |
| `type` | `const` 或 `eq_ref` | 唯一索引等值命中单行 |
| `type` | `ref` | 普通索引等值命中多行 |
| `type` | `range` | 索引范围扫描 |
| `type` | `index` | 扫整棵索引树, 略好于全表 |
| `type` | `ALL` | 全表扫描, 索引没用上 |
| `key` | 索引名 | 实际选中的索引, 空表示没走索引 |
| `rows` | 估算行数 | 远大于返回行数说明效率低 |
| `Extra` | `Using index` | 覆盖索引, 不回表 |
| `Extra` | `Using filesort` | 需要额外排序, 顺序与索引不一致 |

- 顺序: 先看 `type` 与 `key`, 再看 `rows`, 最后看 `Extra`;
- 覆盖: `key` 为空但 `type` 不是 `ALL` 时, 可能走了索引合并;
- 复核: 计划要用真实数据量验证, 小表上的结论不可移植;
