# MySQL 的 MVCC 和间隙锁各解决什么问题？

## 常见问题

- 简述 MySQL MVCC 的实现原理
- 简述 MySQL 的间隙锁

## 概念索引

- 隐藏列: 每行附带的三个系统字段;
- 版本链: 用回滚指针串起来的历史版本;
- undo log: 记录旧值, 支撑回滚与快照读;
- read view: 判断某个版本对当前事务是否可见;
- 快照读: 不加锁的一致性读;
- 间隙锁: 锁住记录之间的空隙, 阻止插入;
- 下一键锁: 记录锁加间隙锁, 用来挡住幻读;

## 隐藏列和版本链怎么组织？

| 列 | 长度 | 作用 |
| --- | --- | --- |
| `DB_TRX_ID` | 6 字节 | 最后修改这一行的事务 ID |
| `DB_ROLL_PTR` | 7 字节 | 指向 undo 段里的一条回滚记录 |
| `DB_ROW_ID` | 6 字节 | 没有主键时生成的行 ID |

```mermaid
graph LR
    A[数据页里的当前行] --> B[undo: 旧版本 1]
    B --> C[undo: 旧版本 2]
    C --> D[链尾]
```

- 更新: 不覆盖旧值, 而是写一条 undo 记录并改回滚指针;
- 链头: 最新版本在数据页, 旧版本在 undo 表空间;
- 清理: 没有事务再需要旧版本时, purge 线程才回收;

## read view 怎么判断可见性？

- 生成: 事务第一次一致性读时创建 read view, 记下当时的活跃事务列表;
- 已提交: 事务 ID 小于列表最小值, 说明早已提交, 可见;
- 未开始: 事务 ID 大于等于下一个待分配 ID, 说明在本快照之后开始, 不可见;
- 活跃区间: 落在列表范围内就逐个比对, 在列表里说明未提交, 不可见;
- 自己: 自己事务写的版本永远可见;
- 回溯: 不可见就沿回滚指针找上一个版本, 直到可见或到链尾;

## 快照读和当前读差在哪？

| 语句 | 读哪个版本 | 加锁 |
| --- | --- | --- |
| 普通 `SELECT` | read view 可见的快照 | 不加锁 |
| `SELECT ... FOR UPDATE` | 最新已提交版本 | 加排他锁 |
| `SELECT ... FOR SHARE` | 最新已提交版本 | 加共享锁 |
| `UPDATE`、`DELETE` | 最新已提交版本 | 加排他锁 |

- 结论: MVCC 只优化读, 写仍然靠锁;
- 生效范围: 读已提交每条语句新建快照, 可重复读整个事务共用一个;
- 症状: 事务里读不到刚提交的数据, 多半是快照建立得太早;

## 间隙锁锁的是什么？

- 定义: 锁住两条索引记录之间的开区间, 不锁记录本身;
- 触发: 可重复读下的范围查询, 以及等值查询没命中任何行;
- 作用: 别的事务无法往这个间隙插入, 于是不会凭空多出行;
- 退化: 唯一索引等值命中唯一一行时, 下一键锁退化成记录锁;
- 冲突: 间隙锁之间通常互不冲突, 但与插入意向锁冲突;

```sql
-- 会话 A: 锁住 (10, 20) 这段间隙
SELECT * FROM t WHERE id BETWEEN 11 AND 19 FOR UPDATE;
-- 会话 B: 插入被阻塞, 直到 A 提交
INSERT INTO t(id) VALUES (15);
```

## 间隙锁的代价是什么？

- 死锁: 两个事务各锁一段间隙再插入, 容易形成环;
- 范围: 扫描范围越大锁越多, 没有索引的范围更新会锁住大量间隙;
- 写延迟: 并发插入密集的表上, 间隙锁会让写入排队;
- 做法: 更新走主键或唯一索引, 缩小范围, 事务尽量短;
- 观察: `SHOW ENGINE INNODB STATUS` 里看 `LOCK WAIT` 与锁模式;
- 手册: 机制细节见 [InnoDB 多版本](https://dev.mysql.com/doc/refman/8.0/en/innodb-multi-versioning.html) 与 [InnoDB 锁](https://dev.mysql.com/doc/refman/8.0/en/innodb-locking.html);
