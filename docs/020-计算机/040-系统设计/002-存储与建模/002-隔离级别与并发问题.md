# 事务隔离级别有哪些，各有什么优缺点？

## 常见问题

- 数据库的事务隔离级别有哪些？各有哪些优缺点？
- 简述脏读和幻读的发生场景，InnoDB 是如何解决幻读的？
- 并发事务会引发哪些问题？如何解决？

## 概念索引

- 隔离级别: 在并发与一致性之间取舍的四档设置;
- 脏读: 读到别人还没提交的数据;
- 不可重复读: 同一事务两次读同一行, 结果不同;
- 幻读: 同一范围两次读, 行数不同;
- 快照读: 按事务可见版本读, 不加锁;
- 当前读: 读最新版本并加锁, 幻读在这里发生;
- 间隙锁: 锁住索引记录之间的空隙, 让新行插不进来;

## 四种级别分别禁止哪些异常？

| 级别 | 脏读 | 不可重复读 | 幻读 |
| --- | --- | --- | --- |
| 读未提交 | 可能 | 可能 | 可能 |
| 读已提交 | 禁止 | 可能 | 可能 |
| 可重复读 (InnoDB 默认) | 禁止 | 禁止 | 快照读禁止, 当前读靠间隙锁 |
| 串行化 | 禁止 | 禁止 | 禁止 |

- 默认: InnoDB 默认 `REPEATABLE READ`, 可用 `transaction_isolation` 调整;
- 顺序: 级别越高约束越强, 并发代价也越大;
- 边界: 隔离级别管的是同一库内并发, 跨库要靠分布式事务;

## 各档隔离级别的优缺点是什么？

| 级别 | 优点 | 缺点 |
| --- | --- | --- |
| 读未提交 | 读不加锁, 最快 | 可能读到回滚数据, 结果不可信 |
| 读已提交 | 每次读最新提交版本, 无脏读 | 同事务多次读结果不一致 |
| 可重复读 | 事务内快照稳定, 逻辑好写 | 长事务撑大 undo, 间隙锁增加死锁 |
| 串行化 | 结果等价于串行执行 | 并发急剧下降, 大量等待与超时 |

- 选择: 多数业务用默认可重复读即可;
- 评估: 写冲突多的热点表可切读已提交, 换取更少间隙锁;
- 权衡: 隔离级别是异常与吞吐之间的取舍, 不是越高越好;

## 三种异常分别怎么发生？

| 场景 | 时刻 | 会话 A | 会话 B |
| --- | --- | --- | --- |
| 脏读 | 1 | `UPDATE` 余额改为 0, 未提交 | 读到余额 0 |
| 脏读 | 2 | `ROLLBACK` | 手上的 0 从未真实存在 |
| 不可重复读 | 1 | 读余额 100 | |
| 不可重复读 | 2 | | `UPDATE` 余额为 200 并提交 |
| 不可重复读 | 3 | 再读余额 200 | 同一事务两次结果不同 |
| 幻读 | 1 | `COUNT` 订单得 5 | |
| 幻读 | 2 | | `INSERT` 一条新订单并提交 |
| 幻读 | 3 | 再 `COUNT` 得 6 | 行数变了, 像出现幻觉 |

- 区别: 不可重复读针对同一行的值, 幻读针对结果集的集合;
- 根源: 都来自并发事务在两次读之间提交了修改;
- 变体: 更新丢失与写偏斜不在这三类里, 要靠加锁或更高隔离;

## InnoDB 怎么解决幻读？

- 快照读: 普通 `SELECT` 走一致性读, 只看事务可见的版本, 新行看不见;
- 当前读: `SELECT ... FOR UPDATE`、`UPDATE`、`DELETE` 读最新版本;
- 加锁: 当前读对扫描范围加下一键锁, 别的会话插不进这个范围;
- 例外: 读已提交下间隙锁基本关闭, 只在外键与唯一键检查时使用;
- 串行化: 普通 `SELECT` 隐式转成 `FOR SHARE`, 读取之间互相阻塞;
- 结论: 快照读靠 MVCC, 当前读靠锁, 两者配合才没有幻读;

## 并发问题除了调级别还能怎么解决？

- 缩小事务: 事务里不放远程调用、文件写入与人工确认;
- 当前读: 需要最新值再做判断时直接加锁读, 不要读后写;
- 唯一约束: 防重复用数据库约束, 不要只靠先查再插;
- 重试: 死锁与锁等待超时都要有退避重试;
- 幂等: 重试的写操作要能识别重复请求;
