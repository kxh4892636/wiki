# SQL 注入怎么防，数据库压测怎么做？

## 常见问题

- 什么是 SQL 注入攻击？如何防止这类攻击？
- 如何设计数据库压测方案？

## 概念索引

- 注入: 用户输入被当成 SQL 代码执行;
- 参数化查询: 值以参数传递, 与语句结构分离;
- 白名单: 标识符无法参数化时用固定集合校验;
- 最小权限: 账号只拿必要的库表权限;
- 压测: 用接近生产的负载测量系统上限;
- 拐点: 加压后延迟与错误率同时恶化的临界点;

## 注入是怎么发生的？

```text
拼出来的语句: SELECT * FROM users WHERE name = '<输入>'
输入 ' OR '1'='1 之后: 条件恒真, 整表被返回
输入 '; DROP TABLE users -- 之后: 引号闭合, 后续变成新语句
```

- 原理: 输入里的引号闭合了字面量, 剩下的内容成为语法;
- 变体: 联合查询读其他表、注释截断、时间盲注、堆叠语句;
- 后果: 拖库、绕过登录、篡改数据、写文件;
- 前提: 只要还在拼接字符串, 业务层的过滤都补不回来;

## 怎么防注入？

| 措施 | 做法 |
| --- | --- |
| 参数化 | 预编译语句传参, 值与结构分离 |
| 白名单 | 表名、列名、排序方向只能来自枚举 |
| 最小权限 | 业务账号不给跨库与 `DROP` 权限 |
| ORM 插值 | 用参数占位, 不拼模板字符串 |
| 输入校验 | 长度、类型、格式先卡一遍 |
| 错误处理 | 不把 SQL 与堆栈回显给前端 |

- 排序: 参数化是根本手段, 其余都是纵深防御;
- 边界: 标识符不能用占位符替代, 只能白名单校验后拼接;
- 兜底: 网关规则与审计日志用于发现异常查询;

## 数据库压测怎么做？

- 目标: 先定 QPS、P99、错误率与资源上限, 再设计负载;
- 数据: 数据量与分布接近生产, 否则全内存命中会高估性能;
- 场景: 按线上读写比构造混合负载, 覆盖事务与批量写;
- 工具: `sysbench` 做基准, 业务侧用真实 SQL 回放;
- 隔离: 压测环境独立, 不共享生产实例;

```text
定目标 → 建基线 → 逐步加压 → 记 P99 与错误率
→ 找拐点 → 定位瓶颈 → 优化 → 同负载回归
```

## 压测要看哪些指标？

| 指标 | 含义 | 异常信号 |
| --- | --- | --- |
| QPS、TPS | 吞吐 | 加压后不再上涨 |
| P99 延迟 | 尾延迟 | 随并发线性上升 |
| 错误率 | 失败比例 | 超时与死锁增多 |
| 锁等待 | `Innodb_row_lock_waits` | 写入成为瓶颈 |
| 连接数 | 活跃与等待连接 | 打满 `max_connections` |
| 缓冲池命中率 | 内存覆盖度 | 明显下降说明数据放不进内存 |

- 判读: 出现拐点就停止加压, 先定位瓶颈再继续;
- 采集: 服务端与客户端指标一起看, 别只看压测工具的汇总;
- 饱和: CPU、IO、连接数任一打满, 延迟就开始恶化;

## 压测结果怎么用？

- 容量: 按拐点的五成到七成定水位, 留出突发余量;
- 回归: 优化前后用同一负载对比, 不看单次绝对值;
- 记录: 保存数据规模、并发模型与参数, 便于复现与复盘;
- 手册: 攻击类型与案例见 [OWASP SQL Injection](https://owasp.org/www-community/attacks/SQL_Injection);
