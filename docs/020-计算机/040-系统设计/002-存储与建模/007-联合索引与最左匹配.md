# 联合索引为什么遵守最左匹配？

## 常见问题

- 简述什么是最左匹配原则
- 联合索引的存储结构是什么？
- MySQL 联合索引底层原理是什么？
- 假设建立联合索引 (a, b, c) 如果对字段 a 和 c 查询，会用到这个联合索引吗？
- 建立了三个单列索引 a, b, c 查询 where a = ? b = ? c = ？索引会起作用吗？

## 概念索引

- 联合索引: 多个列拼成一个键的索引;
- 字典序: 先按第一列排, 相同再按第二列排;
- 最左匹配: 只有从最左列起连续的前缀才能用于定位;
- 索引下推: 在索引层先过滤, 减少回表次数;
- 索引合并: 优化器把多个单列索引的结果拼起来;
- 覆盖: 需要的列都在索引里, 不再回表;

## 联合索引在磁盘上怎么排？

| a | b | c |
| --- | --- | --- |
| 1 | 1 | 3 |
| 1 | 2 | 1 |
| 1 | 2 | 5 |
| 2 | 1 | 1 |

- 排序: 先按 a, a 相同按 b, b 相同按 c;
- 叶子: 存 (a, b, c) 与主键值;
- 推论: a 全局有序, b 只在 a 相同时有序, c 只在 (a, b) 相同时有序;
- 页内: 同样按上述顺序排列, 页间也按键值递增串成链表;

## 最左匹配到底匹配什么？

- 规则: `WHERE a = ? AND b = ?` 能用, `WHERE b = ?` 不能用;
- 原因: 不给 a 就无法在树上定位, b 的局部有序帮不上忙;
- 范围: `WHERE a = ? AND b > 2 AND c = 3` 只能用到 a 与 b;
- 断裂: 范围条件之后 b 有多个取值, c 不再全局有序;
- 排序: `ORDER BY a, b` 能复用索引顺序, `ORDER BY b, a` 不行;
- 结论: 等值列放前面, 范围列与排序列放后面;

## (a, b, c) 查 a 和 c 会用到索引吗？

- 部分用到: a 能把范围缩到 a 相同的所有行;
- 无法定位: c 在索引里不是全局有序, 因为缺了中间列 b;
- 下推: MySQL 5.6 起可把 c 条件下推到索引层过滤, 减少回表;
- 判读: `Extra` 显示 `Using index condition` 说明发生了下推;
- 改法: 给高频组合另建 `(a, c)`, 或把 b 补进查询条件;

```sql
-- key_len 只覆盖 a 时, 说明 c 没参与定位
EXPLAIN SELECT * FROM t WHERE a = 1 AND c = 3;
```

## 三个单列索引会同时生效吗？

- 默认: 一张表一次通常只用一个索引, 其余条件回表后过滤;
- 选择: 优化器挑区分度高、扫描行数少的那个;
- 例外: `index_merge` 可以把两个索引取交集或并集;
- 代价: 索引合并要额外排序去重, 不总是比单索引快;
- 对比: 三列总是同时过滤, 联合索引通常优于三个单列索引;

## EXPLAIN 怎么读联合索引？

| 观察点 | 判读 |
| --- | --- |
| `key` | 选中哪个索引, 可能不止一个 |
| `key_len` | 用了几个列, 每列按类型算长度 |
| `type=ref` | 前缀等值匹配 |
| `type=range` | 前缀等值加范围扫描 |
| `Extra=Using index` | 覆盖, 不回表 |
| `Extra=Using index condition` | 下推, 索引层过滤后再回表 |
| `Extra=Using where` | 回表后再过滤, 说明有列没进索引 |

- 前缀: `key_len` 明显小于索引定义长度, 说明只用了前几列;
- 回表: 出现 `Using where` 说明过滤发生在回表之后;
- 手册: 下推规则见 [索引条件下推](https://dev.mysql.com/doc/refman/8.0/en/index-condition-pushdown-optimization.html), `type` 次序见 [EXPLAIN 输出](https://dev.mysql.com/doc/refman/8.0/en/explain-output.html);
