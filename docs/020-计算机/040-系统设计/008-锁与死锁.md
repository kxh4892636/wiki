# 乐观锁和悲观锁有什么区别，死锁怎么解决？

## 常见问题

- 简述乐观锁以及悲观锁的区别以及使用场景
- 产生死锁的必要条件有哪些？如何解决死锁？
- 什么是公平锁？什么是非公平锁？

## 概念索引

- 悲观锁: 先加锁再改, 假设一定会冲突;
- 乐观锁: 先改再看版本, 假设通常不冲突;
- 版本号: 用一列或时间戳判断数据是否被改过;
- 死锁: 两个事务互相持有对方要的锁;
- 等待图: 用有向边表示谁在等谁;
- 公平锁: 按到达顺序授予, 不插队;
- 非公平锁: 允许插队, 吞吐更高;

## 悲观锁怎么写，适合什么场景？

- 写法: `SELECT ... FOR UPDATE` 加排他锁, `FOR SHARE` 加共享锁;
- 效果: 被锁住的行在事务提交前, 别人改不了也拿不到写锁;
- 场景: 库存扣减、账户余额、订单状态机迁移;
- 优点: 逻辑直接, 冲突时排队等待而不是反复重试;
- 缺点: 阻塞与死锁风险高, 长事务会拖住整条调用链;
- 注意: 锁的是索引记录, 条件没走索引就退化成锁很多行;

## 乐观锁怎么写，适合什么场景？

```sql
UPDATE account
   SET balance = balance - 100, version = version + 1
 WHERE id = 1 AND version = 7;
-- 影响行数为 0: 版本已被别人改过, 重读后重试
```

- 核心: 用 `WHERE version = ?` 做一次比较并交换;
- 场景: 读多写少、冲突概率低的更新, 以及跨服务的状态校验;
- 优点: 不加锁不占连接, 失败可重试;
- 缺点: 冲突多时重试放大, 重试与上限必须自己写;
- 变体: 用状态字段做条件更新, 效果等同版本号;

## 死锁的四个必要条件是什么？

| 条件 | 含义 | 怎么打破 |
| --- | --- | --- |
| 互斥 | 资源一次只给一个事务 | 用乐观锁或只读副本减少争用 |
| 占有并等待 | 拿着锁还去申请新锁 | 一次性申请, 按固定顺序加锁 |
| 不可抢占 | 已持有的锁不能被强行夺走 | 设锁等待超时, 让它失败重试 |
| 循环等待 | 等待关系成环 | 统一加锁顺序, 打断环 |

```mermaid
graph LR
    A[事务 1: 持有行 1, 等行 2] --> B[事务 2: 持有行 2, 等行 1]
    B --> A
```

- 检测: InnoDB 默认开启死锁检测, 发现环立即回滚其中一方;
- 代价: 高并发下检测本身耗 CPU, 可关掉检测改用锁等待超时;
- 报错: 应用侧会收到 `Deadlock found when trying to get lock`;

## 怎么减少死锁？

- 顺序: 多行更新按主键升序, 别让两个事务反着来;
- 索引: 更新条件走索引, 否则扫到的行全被锁住;
- 批量: 大批量更新切成小批, 但别把事务拉长;
- 事务: 事务内不调用远程服务, 不等人工确认;
- 重试: 死锁与锁超时要退避重试有限次, 并保证幂等;
- 排查: `SHOW ENGINE INNODB STATUS` 的 `LATEST DETECTED DEADLOCK`;

## 公平锁和非公平锁是什么？

- 公平锁: 线程按请求顺序排队拿锁, 先到先得;
- 非公平锁: 新来的线程可以先抢, 抢不到再排队;
- 取舍: 公平锁等待时间可预期, 非公平锁减少唤醒开销、吞吐更高;
- 代码例子: Java 里 `new ReentrantLock(true)` 是公平锁;
- 数据库侧: InnoDB 没有公平开关, 只用 `innodb_lock_wait_timeout` 兜底;
- 手册: 死锁检测与处理见 [InnoDB 中的死锁](https://dev.mysql.com/doc/refman/8.0/en/innodb-deadlocks.html);
