# CAP、最终一致性与幂等是什么关系？

## 常见问题

- 简述 CAP 理论
- 什么是 CAP ？什么是最终一致性？什么是幂等操作？
- kafka 如何保证消息一致性？

## 概念索引

- C 一致性: 读到的结果像同一副本按实时顺序执行;
- A 可用性: 每个非故障节点都要在有限时间给出非错误响应;
- P 分区容忍: 节点间消息可能丢失, 这是必须承受的条件;
- CP: 分区时限制可能不一致的操作;
- AP: 分区时继续服务, 允许读旧值与并发冲突;
- 最终一致性: 停止写入并修复后, 各副本收敛到同一状态;
- 幂等: 同一请求执行多次只产生一次效果;
- 幂等红线: 最终一致性依赖幂等, 否则重试会把临时偏差变成永久错误;

## CAP 究竟限制了什么？

- 不是三选二: 分区是网络属性, 不能关掉, 只能在分区发生时选择放弃 C 或 A;
- 一致性含义: 这里是线性一致性, 不是事务的 ACID 一致性;
- 可用性含义: 返回错误不算可用, 也不能无限期不回应;
- 依据: [Gilbert 与 Lynch 的证明](https://www.cs.princeton.edu/courses/archive/spr22/cos418/papers/cap.pdf);
- 常见误用: 把单机数据库说成 CA, 只是它没被分区打到;
- 场景: 同机房内网络可靠, 但跨机房一定会有分区;

## 分区发生时 CP 与 AP 怎么选？

| 选择 | 分区时的行为 | 业务代价 |
| --- | --- | --- |
| CP | 无法安全协调的一侧拒绝写或拒绝读 | 部分请求失败 |
| AP | 可达节点继续读写 | 读到旧值, 冲突需合并 |

- 选 CP: 余额、库存、配置变更这类不能错的写;
- 选 AP: 商品浏览、动态流、计数这类可以暂时旧的读;
- 同系统混用: 下单走 CP, 推荐位走 AP;
- 决策依据: 先写清允许读多旧、能等多久、失败怎么降级;

## 为什么还要看 PACELC？

- PACELC 前半: 分区 P 时在 A 与 C 之间选;
- 后半: 否则在正常 E 下, 在延迟 L 与一致性 C 之间选;
- 正常路径也有代价: 跨区等副本确认, 要付一个往返时间;
- 取舍: 同步复制换一致, 异步复制换延迟;
- 用法: 指标里同时给一致性与 P99 延迟目标;

## 最终一致性怎么才算做到了？

- 收敛条件: 停止新增写入, 且复制与修复持续推进;
- 观测: 记录每个副本的最新版本或位点, 观察到齐;
- 读己之写: 用户写完后立刻读, 要能读到自己的修改;
- 冲突策略: 谁赢要提前定义, 例如版本号大的胜或业务合并;
- 中间态: 界面上要能表达处理中, 而不是显示错误数据;
- 反例: 只说以后总会一致, 不给出收敛时间与验证方法;

## 幂等是怎么实现的？

| 手段 | 做法 | 适用 |
| --- | --- | --- |
| 唯一键 | 业务单号加唯一索引, 重复插入失败 | 创建类操作 |
| 状态机 | 只允许特定状态迁移, 重复请求直接返回 | 订单、支付 |
| 去重表 | 记录已处理的请求 ID 与结果 | 跨服务调用 |
| 版本号 | 更新带 version 条件, 不匹配就不生效 | 覆盖写 |
| Token | 先取一次性令牌, 使用时核销 | 表单提交 |

- 超时重试: 客户端超时不等于服务端没执行, 必须能安全重试;
- 幂等键: 由业务生成并透传, 不能靠服务端新生成;
- 有效期: 去重记录要有保留期, 兼顾存储与重放窗口;

## Kafka 怎么保证消息一致性？

- 副本写入: acks=all 让主库等 ISR 全部写入再回成功;
- 最小同步副本: min.insync.replicas=2 时, 只剩一个副本就拒绝写;
- 生产者幂等: enable.idempotence 加序列号去重, 防重试造成重复;
- 事务: 跨分区原子写, 消费端 read_committed 才看得到已提交消息;
- 选举约束: 关闭 unclean.leader.election, 避免落后副本当主;
- 边界: 一致性指副本与读写语义, 端到端业务正确仍要幂等兜底;

## 三者怎么串起来？

- CAP 决定分区时的取舍, 最终一致性是选 AP 后的收敛目标;
- 幂等是把重试、重复投递这些不安全因素关掉的前提;
- 落地顺序: 先定一致性目标, 再定幂等键, 最后压测收敛时间;
