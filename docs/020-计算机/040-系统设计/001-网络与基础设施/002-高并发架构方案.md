# 高并发系统如何设计, QPS 翻十倍时怎么办?

## 常见问题

- 了解高并发的解决方案吗？例如动静分离，缓存，负载均衡
- 假如明天是活动高峰？QPS 预计会翻10倍，你要怎么做？
- 如何测试应用的 QPS？

## 概念索引

- 动静分离: 静态资源交给 CDN 与 Nginx;
- 缓存: 用局部数据挡住重复读;
- 负载均衡: 把流量摊到多个实例, 前提是应用无状态;
- 削峰: 用队列把突发写请求摊平;
- 限流与降级: 超额时先保核心链路;
- 压测: 用可复现流量测出容量上限, 限流阈值就来自它;

## 高并发手段分哪几层?

| 层 | 手段 | 典型做法 |
| --- | --- | --- |
| 客户端 | 少发请求 | 合并接口、本地缓存、懒加载 |
| 接入 | 就近与分担 | CDN、动静分离、L4 与 L7 负载均衡 |
| 应用 | 变多与变快 | 无状态水平扩容、线程池隔离、异步化 |
| 缓存 | 少打数据库 | 本地加 Redis 多级、热点预热 |
| 数据 | 分摊读写 | 读写分离、分库分表、批量写 |
| 保护 | 挡住超额 | 限流、熔断、降级、排队 |

- 动静分离: 图片与脚本走 CDN, 动态请求才回源, 回源带宽直接降一个量级;
- 缓存: 收益来自命中率, 命中率不到七成的缓存基本只增加复杂度;
- 异步化: 发券、积分、通知这类非主链路动作进队列, 前台只写核心数据;

## 翻十倍前先算什么?

- 算账: 峰值 = 日常峰值 × 10, 按接口拆开算, 一个总数字没法定位瓶颈;
- 压测找限: 逐层看 CPU、连接数、慢 SQL、下游限流, 先找最先饱和的一项;
- 预案: 提前写好降级与回滚步骤, 别在高峰现场改配置;

## 当天需要做什么?

- 扩容: 无状态应用加副本, 提前预热 JIT、缓存与连接池;
- 减压: 加缓存、读走从库、写进队列;
- 兜底: 全局限流加降级开关, 准备静态兜底页;
- 活动期: 关掉非核心功能, 盯 P99 与错误率而不是只看平均值;

| 信号 | 多半卡在 | 动作 |
| --- | --- | --- |
| CPU 打满 | 计算或序列化 | 扩容、减日志、换协议 |
| CPU 低但 RT 高 | 等锁或等下游 | 查连接池、慢查询、下游超时 |
| 队列堆积 | 消费能力不足 | 加消费者、批量处理 |
| 数据库 QPS 高 | 缓存没挡住 | 提命中率、读写分离 |

- 并发换算: 并发数约等于 QPS 乘以平均耗时, 1000 QPS 配 50ms 需要 50 个并发;
- 池子: 连接池与线程池都要大于目标并发, 否则排队会把延迟放大成雪崩;

## 如何测出应用的真实 QPS?

- 工具: wrk、JMeter、k6、Gatling 都能压 HTTP, 脚本与数据要固定;
- 环境: 压测环境与生产同规格, 或用全链路压测加影子库;
- 指标: QPS、P95 与 P99、错误率、CPU 与 GC、连接池与队列深度;
- 方法: 阶梯加压, 找错误率或 P99 突然抬升的拐点, 该点即容量上限;
- 陷阱: 压测机自己先打满, 单台发压不够就用多台或云压测;

```bash
wrk -t8 -c400 -d60s --latency http://host/api/items
```

- 复现: 把压测脚本与数据版本一起入库, 结果才可比较;
