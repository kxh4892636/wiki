# 缓存与数据库不一致怎么解决, 热点 key 怎么处理?

## 常见问题

- 如何解决缓存与数据库不一致的问题？
- 如何解决缓存与数据库不一致的问题？
- 简述 Redis 如何处理热点 key 访问

## 概念索引

- 旁路缓存: 读走缓存, 未命中回源再回填;
- 失效优先: 写库后删缓存, 而不是更新缓存;
- 延迟双删: 删缓存后延迟再删一次, 覆盖读回填的旧值;
- 最终一致: 用 TTL、重试与 binlog 订阅把窗口压到可接受;
- 热点 key: 单键流量超过单个分片的处理能力;
- 本地缓存: 把热点再往前挪一层, 是热点 key 最直接的解法;

## 不一致从哪来?

| 场景 | 现象 | 根因 |
| --- | --- | --- |
| 并发读写 | 旧值被回填 | 读未命中与写库交错 |
| 先更缓存后写库 | 缓存是新值库是旧值 | 库写失败 |
| 主从延迟 | 回填旧快照 | 读到了延迟的从库 |
| 删除失败 | 缓存长期旧值 | 没有 TTL 兜底 |

```text
T1 写: 删缓存
T2 读: 未命中, 读库拿到旧值
T1 写: 更新库为新值
T2 读: 把旧值回填进缓存   -> 不一致
```

- 双写: 同时写缓存与库, 两步无法保证都成功;
- 结论: 两次操作之间必然有窗口, 目标是把窗口压小并保证最终收敛;

## 主流方案怎么选?

| 方案 | 做法 | 代价 |
| --- | --- | --- |
| 写库后删缓存 | Cache Aside, 默认选择 | 极小概率脏读 |
| 延迟双删 | 删缓存, 写库, 延迟再删 | 延迟要大于一次读耗时 |
| 更新缓存 | 写库后回写新值 | 并发写会乱序, 不推荐 |
| 订阅 binlog | Canal 解析后删缓存 | 有异步延迟 |
| 消息重试 | 删除失败进队列重试 | 要保证消息不丢 |
| 读写都走库 | 关键路径放弃缓存 | 性能差 |

- 默认: 读多写少用 Cache Aside, 加 TTL 兜底就够;
- 强一致: 按 key 加分布式锁让写串行, 或用版本号校验;
- 兜底: 删除失败要重试, 重试仍失败就等 TTL 过期;
- 顺序: 先写库再删缓存, 顺序反了会把旧值留在缓存里;

## 热点 key 怎么处理?

- 识别: 用 `redis-cli --hotkeys` 或代理层统计, 单键到万级 QPS 就该处理;
- 本地缓存: 进程内用 Caffeine 挡一层, 配短 TTL 或广播失效;
- key 拆分: 把 hot:1 拆成 hot:1:0 到 9, 读时随机选一个, 才突破单分片上限;
- 副本: 读多写少的热点建多副本, 读时随机挑, 分散单节点压力;
- 限流: 对单 key 的读加令牌桶, 超额走降级;
- 预热: 活动前批量灌入缓存, 避免开服瞬间同时回源;
