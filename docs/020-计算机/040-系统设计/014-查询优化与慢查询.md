# 慢查询怎么定位，SQL 与 MySQL 怎么优化？

## 常见问题

- SQL优化的方案有哪些，如何定位问题并解决问题？
- MySQL 有什么调优的方式？
- 如何定位以及优化数据库慢查询

## 概念索引

- 慢查询日志: 记录执行时间超过阈值的语句;
- EXPLAIN: 看优化器选了哪条访问路径;
- 覆盖索引: 减少回表与随机 IO;
- 缓冲池: InnoDB 缓存数据页与索引页的内存区域;
- 参数调优: 调整内存、日志与连接相关变量;
- 连接池: 复用连接, 避免反复建连与线程风暴;

## 怎么定位慢查询？

- 开启: `slow_query_log=ON`, 阈值 `long_query_time` 默认 10 秒, 常调到 0.1;
- 计时: 慢日志记的是执行时间, 不包含等锁与等 IO 的时间;
- 归并: 用 `mysqldumpslow` 或 `pt-query-digest` 按语句指纹聚合;
- 复盘: 对 Top SQL 跑 `EXPLAIN`, 再用真实参数看实际行数;
- 排序: 先修扫描行数最多的语句, 不是耗时最长的孤例;

```text
慢日志 → 指纹归并 → EXPLAIN → 改 SQL 或索引 → 回归对比
```

## EXPLAIN 应该看什么？

| 列 | 判读 |
| --- | --- |
| `type` | 从 `const`、`eq_ref`、`ref`、`range` 到 `index`、`ALL` 越来越差 |
| `key`、`key_len` | 实际用了哪个索引、几列 |
| `rows`、`filtered` | 估算扫描行数与过滤率, 乘积才是候选行数 |
| `Extra` | `Using filesort`、`Using temporary` 是优化信号 |

- 误判: 小表上全表扫描常常就是最优计划;
- 复核: 用 `EXPLAIN ANALYZE` 看真实耗时分布;
- 放弃: `possible_keys` 有值而 `key` 为空, 是优化器主动不用索引;

## SQL 层面怎么优化？

| 问题 | 改法 |
| --- | --- |
| 返回列太多 | 只取需要的列, 尽量走覆盖索引 |
| 深分页 | 用游标或记住上次最大主键 |
| 相关子查询 | 改成 `JOIN` 或 `EXISTS`, 避免逐行执行 |
| 大事务 | 拆批提交, 缩短锁持有时间 |
| `OR` 与负向条件 | 改 `UNION` 或补索引 |
| 批量写 | 一次插多行, 按列数乘行数切批 |

- 底线: 关联列与过滤列必须有索引, 否则退化成 N 次全表扫描;
- 写法: 避免 `SELECT *`, 避免在过滤列上做运算与函数;
- 分段: 分页与聚合先缩小范围再计算, 不要先全表算再筛;

## 库层面怎么调优？

- 内存: `innodb_buffer_pool_size` 通常给到物理内存的一半以上;
- 日志: `innodb_log_file_size` 影响写吞吐与崩溃恢复时长;
- 并发: `max_connections` 与连接池上限要匹配, 避免线程风暴;
- 结构: 大表归档、冷热分离、按时间分区;
- 架构: 读多加只读副本, 写多再考虑分库分表;

## 哪些优化其实是误区？

- 平均值: 平均正常但 P99 很慢, 用户照样卡;
- 堆索引: 每个字段都建索引, 写入成倍变慢;
- 早优化: 小数据量的计划不可移植到生产;
- 只看 SQL: 锁等待、连接池耗尽、复制延迟也会表现为慢;
