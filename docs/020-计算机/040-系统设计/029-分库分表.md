# 什么情况下该分库, 什么情况下该分表？

## 常见问题

- 简述数据库中什么情况下进行分库，什么情况下进行分表？

## 概念索引

- 分表: 把一张大表拆成结构相同或不同的多张;
- 分库: 把数据分散到多个数据库实例;
- 水平拆分: 按行拆, 每张表结构一致;
- 垂直拆分: 按列或按业务拆, 表结构不同;
- 分片键: 决定一行数据去哪个分片的字段;
- 跨片查询: 分片键没带上的查询, 只能合并多个分片的结果;

## 先确认瓶颈到底在哪？

| 现象 | 先怀疑 | 处理顺序 |
| --- | --- | --- |
| 单条查询慢 | 索引缺失、回表多 | 加索引、改写 SQL |
| 写入慢 | 锁竞争、磁盘 IO | 拆事务、加缓存、读写分离 |
| 连接打满 | 连接池与实例上限 | 连接池复用、加从库、分库 |
| 单表过大 | 表与索引体积 | 归档、分区表、分表 |
| 磁盘将满 | 历史数据堆积 | 冷热分离、归档 |

- 顺序: 先优化 SQL 与索引, 再读写分离与缓存, 最后才拆;
- 反例: 没定位瓶颈就分库分表, 复杂度上去了问题还在;

## 什么情况该分表？

- 单表行数上亿: 索引层数变深, 查询与 DDL 都变慢;
- 单表体积过大: 备份与恢复时间长, 迁移困难;
- 写入热点集中: 自增主键尾部插入争抢, 页分裂明显;
- 历史数据多: 老数据很少访问, 可以按时间拆开;
- 做法: 水平按分片键散开, 或垂直把大字段拆到扩展表;
- 收益: 单表变小, 索引变浅, 批量操作更快;

## 什么情况该分库？

- 连接数打满: 单实例连接上千后调度开销剧增;
- CPU 或 IO 打满: 一台机器扛不住全部写入;
- 业务隔离: 不同租户或业务线要独立故障域与权限;
- 合规要求: 数据要分地域存放;
- 做法: 按业务垂直拆库, 或按分片键水平拆库;
- 收益: 请求分散到多台, 单库故障只影响一部分数据;

## 分片键怎么选？

- 高基数: 取值多才散得开, 性别这类字段不行;
- 查询高频: 最常见的查询条件要能带上分片键, 否则要广播;
- 均匀: 避免某个值占了大半数据, 例如大客户;
- 稳定: 分片键不要变, 变一次就要迁数据;
- 组合: 订单按用户 ID 分片, 同时冗余一份按商家查的表;
- 兜底: 用基因法把关联键塞进 ID, 让关联查询落在同一片;

## 拆分后要付出什么代价？

- 跨库 join: 只能改成多次查询加内存拼装, 或冗余宽表;
- 分布式事务: 跨片写要么两阶段提交, 要么最终一致加补偿;
- 全局排序分页: 每个分片各取前 N 条再合并, 深分页代价高;
- 全局唯一 ID: 自增失效, 要用号段或雪花算法;
- 扩容迁移: 取模分片要全量搬迁, 一致性哈希或双倍扩容更平滑;
- 运维: 表数量翻倍, 监控、备份与 DDL 都要按分片批量执行;

## 拆分的落地顺序是什么？

- 第一步: 索引与慢查询治理, 通常能解决大部分问题;
- 第二步: 读写分离加缓存, 分摊读压力;
- 第三步: 冷热分离与归档, 先把历史数据挪走;
- 第四步: 垂直拆业务, 把一个库按域切开;
- 第五步: 水平分片, 用中间件或客户端分片;
- 迁移: 双写加校验, 灰度切读, 确认后再切写;
