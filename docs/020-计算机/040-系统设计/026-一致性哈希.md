# 一致性哈希为什么能减少扩容时的数据迁移？

## 常见问题

- 简述一致性哈希算法的实现方式及原理

## 概念索引

- 取模映射: 用 hash 值对节点数取余选节点;
- 哈希环: 把键与节点映射到同一个首尾相接的空间;
- 顺时针归属: 键交给环上顺时针第一个节点;
- 虚拟节点: 一个物理机映射到环上多个位置;
- 数据倾斜: 区间大小不均导致负载不均;
- 热点键: 数据倾斜的极端情形, 单个键压垮一台机器, 环拆不开;

## 取模映射在扩容时错在哪？

```text
旧: node = hash(key) mod 4
新: node = hash(key) mod 5
绝大多数键的余数都变了, 需要搬家
```

- 迁移量: 节点数从 N 到 N+1, 期望有 K 乘以 N/(N+1) 的键要迁移;
- 后果: 缓存集体失效, 数据库短时间承受全量回源;
- 根因: 节点数直接参与计算, 一变就影响所有键;

## 哈希环怎么选节点？

```text
把 0 到 2^32-1 首尾相接看成一个环
键与节点都用同一个哈希函数落到环上
键归属顺时针方向的第一个节点
```

- 加入节点: 新节点只接管自己到前驱之间的一段, 其他区间不动;
- 移除节点: 它的区间整体交给后继节点;
- 迁移量: 理想均匀时有 N 个节点, 增删一个只影响约 K/N 的键;
- 前提: 所有参与者看到同一份环上成员视图;
- 单调性: 已有键到节点的映射, 不会因为加节点而整体重排;

## 为什么需要虚拟节点？

- 问题: 节点少时随机落点容易形成大区间, 负载天然不均;
- 做法: 对 "节点标识加序号" 再做哈希, 一个物理机占几十上百个位置;
- 收益: 每个物理机负责很多小区间, 方差显著下降;
- 权重: 性能强的机器配更多虚拟节点, 承接更多键;
- 故障: 一台机器挂掉, 它的多个小区间由多台机器分担;
- 代价: 映射表更大, 需要额外维护成员变更;

```text
node-a#1 -> 0x1f3c...
node-a#2 -> 0x7b02...
node-b#1 -> 0x45aa...
同一物理机有多个环上位置, 负载被摊开
```

## 最小实现长什么样？

```python
import bisect
import hashlib

class Ring:
    def __init__(self, nodes, replicas=100):
        self.ring = {}
        self.keys = []
        for node in nodes:
            for i in range(replicas):
                h = self._hash(f"{node}#{i}")
                self.ring[h] = node
                self.keys.append(h)
        self.keys.sort()

    @staticmethod
    def _hash(s):
        return int(hashlib.md5(s.encode()).hexdigest()[:8], 16)

    def get(self, key):
        if not self.keys:
            raise RuntimeError("empty ring")
        h = self._hash(key)
        idx = bisect.bisect(self.keys, h)
        if idx == len(self.keys):
            idx = 0
        return self.ring[self.keys[idx]]
```

- 排序加二分: 查找是 O(log N), 不需要遍历所有节点;
- 环尾回到环头: 超出最大位置时取第一个节点;
- 哈希选择: 生产上用 md5 或 xxhash, 要求分布均匀且稳定;

## 一致性哈希有哪些失效风险？

- 热点键: 千万请求压在一个键上, 仍只落一台机器;
- 级联故障: 一台机器挂了, 负载推给邻居, 邻居扛不住继续挂;
- 成员抖动: 频繁上下线会反复触发迁移, 比故障本身更贵;
- 视图不一致: 不同客户端缓存了不同的环, 同一键会送错位置;
- 缓解: 副本读、热点拆分、限流与稳定成员管理;
- 边界: 它只决定数据放哪, 不负责一致性与持久性;
