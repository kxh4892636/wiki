# TCP 如何建立和释放连接？

## 常见问题

- 简述 TCP 三次握手以及四次挥手的流程。为什么需要三次握手以及四次挥手？
- 简述 TCP 的 TIME_WAIT 和 CLOSE_WAIT
- TCP 挥手时出现大量 CLOSE_WAIT 或 TIME_WAIT 怎么解决？
- TCP 中 SYN 攻击是什么？如何防止？
- 什么是 SYN flood，如何防止这类攻击？
- 简述 TCP 半连接发生场景

## 概念索引

- 三次握手: 同步双方初始序号并确认收发能力;
- 四次挥手: 双方各自关闭发送方向;
- 半连接: 服务器已回 SYNACK、还没收到最终 ACK;
- TIME_WAIT: 主动关闭方的等待状态;
- CLOSE_WAIT: 被动关闭方等待应用关闭;
- SYN flood: 大量半连接耗尽服务器资源;
- SYN cookie: 无状态构造序号，延迟分配连接;

## 三次握手流程是什么？

```text
客户端                          服务器
  | ---- SYN, seq=x -----------> |
  | <--- SYN+ACK, seq=y, ack=x+1 |
  | ---- ACK, ack=y+1 ---------> |
  |        ESTABLISHED           |
```

| 步骤 | 报文 | 关键字段 | 状态变化 |
| --- | --- | --- | --- |
| 1 | SYN | seq=client_isn | 客户端进入 SYN_SENT |
| 2 | SYN+ACK | seq=server_isn, ack=client_isn+1 | 服务器进入 SYN_RCVD |
| 3 | ACK | ack=server_isn+1 | 双方进入 ESTABLISHED |

## 为什么需要三次握手？

- 确认收发: 双方都确认自己和对方的发送、接收能力正常;
- 同步序号: 交换初始序号，后续按字节编号与确认;
- 防旧连接: 避免历史重复 SYN 被服务器误当成新连接;
- 资源分配: 服务器在第二次握手后分配缓存，第三次确认才正式建立;

## 四次挥手流程是什么？

```text
主动关闭方                      被动关闭方
  | ---- FIN, seq=u -----------> |
  | <--- ACK, ack=u+1 ---------- |
  | <--- 剩余数据 --------------- |
  | <--- FIN, seq=v ------------ |
  | ---- ACK, ack=v+1 ---------> |
  |        TIME_WAIT             |
```

| 步骤 | 报文 | 含义 |
| --- | --- | --- |
| 1 | FIN | 主动方没有数据要发送 |
| 2 | ACK | 被动方确认收到 FIN |
| 3 | FIN | 被动方数据发完，准备关闭 |
| 4 | ACK | 主动方确认，进入 TIME_WAIT |

## 为什么需要四次挥手？

- 半关闭: TCP 是全双工，两个方向独立关闭;
- 数据未发完: 收到 FIN 只表示对方不再发送，本端可能还有数据;
- 先确认再发送: 先 ACK，等剩余数据发完再发自己的 FIN;
- 可靠关闭: 双方都确认对方不再发送，避免数据丢失;

## TIME_WAIT 与 CLOSE_WAIT 有什么区别？

| 项 | TIME_WAIT | CLOSE_WAIT |
| --- | --- | --- |
| 谁进入 | 主动关闭方 | 被动关闭方 |
| 时机 | 发完最后一个 ACK 后 | 收到 FIN 并回 ACK 后 |
| 等待什么 | 2MSL，确保 ACK 到达并让旧报文消失 | 应用调用 close |
| 大量出现 | 主动关闭过多、短连接过多 | 应用没有关闭 socket |

```bash
ss -tan state time-wait
ss -tan state close-wait
```

- TIME_WAIT 作用: 最后一个 ACK 丢失时，对方重发 FIN，本端还能再回 ACK;
- TIME_WAIT 作用: 让旧连接的重复报文在网络中过期，避免污染新连接;
- CLOSE_WAIT 大量: 通常是代码漏掉 close，或连接池只借不还;
- TIME_WAIT 大量: 短连接频繁主动关闭、端口耗尽;

## 大量 TIME_WAIT 或 CLOSE_WAIT 怎么处理？

| 现象 | 优先动作 |
| --- | --- |
| CLOSE_WAIT 多 | 查应用是否 close、连接池是否泄漏、回调是否异常 |
| TIME_WAIT 多 | 用连接池复用、减少主动关闭、扩端口范围 |
| 两者都多 | 查请求模式是否短连接、超时与重试是否过多 |

- `tcp_tw_reuse` 只适合客户端主动连接复用，需确认内核与 NAT 行为;
- `tcp_tw_recycle` 在 NAT 环境有风险，现代内核已移除;
- 调参数只能缓解，根因通常是连接管理;

## 半连接与 SYN flood 是什么？

- 半连接: 服务器回 SYNACK 后进入 SYN_RCVD，等待最终 ACK;
- 正常半连接: 持续时间短，队列很快释放;
- SYN flood: 攻击者发大量 SYN，不回最终 ACK，占满半连接队列;
- 后果: 新连接被丢弃，正常用户无法建立连接;
- 放大: 源 IP 伪造时，SYNACK 发往受害者，形成反射;

## 如何防御 SYN flood？

| 手段 | 做法 |
| --- | --- |
| SYN cookie | 不保存半连接，把状态编码进 seq，收到 ACK 再分配 |
| 队列调大 | 提高 backlog 与半连接队列上限，争取处理时间 |
| 缩短超时 | 加快半连接回收 |
| 限速与清洗 | 防火墙、负载均衡按源限速或清洗 |
| anycast / CDN | 分散攻击流量 |

```text
SYN cookie:
server_isn = hash(src_ip, src_port, dst_ip, dst_port, secret, time)
收到 ACK 时重新计算并校验，合法才创建连接
```

- SYN cookie 代价: 部分 TCP 选项无法保存，性能与功能有取舍;
- 云环境优先用云厂商的 DDoS 清洗与 SYN 代理;
