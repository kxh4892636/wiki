# 常用设计模式有哪些, 发布订阅又是怎样实现的？

## 常见问题

- 什么是设计模式，描述几个常用的设计模式
- 简述发布订阅模式的实现方式以及原理

## 概念索引

- 设计模式: 对反复出现的职责分配方式命名;
- 创建型: 管对象怎么创建;
- 结构型: 管对象怎么组合;
- 行为型: 管对象怎么交互;
- 观察者: 目标直接通知自己的观察者;
- 订阅中心: 把观察者升级成互不相识的发布订阅;

## 设计模式是什么？

- 定义: 面向对象设计中可复用的类与对象协作结构;
- 本质: 给常见问题起名, 让讨论从语法上升到职责;
- 边界: 模式不是代码模板, 与语言无关, 也不保证更好;
- 滥用: 强行套模式会增加间接层, 让调用链变长;

| 类型 | 关注点 | 代表 |
| --- | --- | --- |
| 创建型 | 对象创建 | 单例、工厂方法、生成器 |
| 结构型 | 组合方式 | 适配器、装饰、代理 |
| 行为型 | 对象交互 | 策略、观察者、职责链 |

## 常用模式有哪些？

| 模式 | 解决什么 | 典型场景 |
| --- | --- | --- |
| 单例 | 全局只有一个实例 | 配置、连接池 |
| 工厂方法 | 创建逻辑与使用分离 | 按类型造不同实现 |
| 策略 | 算法可替换 | 计费、排序、风控规则 |
| 装饰 | 动态叠加能力 | 中间件、日志与缓存包装 |
| 观察者 | 状态变化通知多方 | 事件监听、状态订阅 |

- 选择: 变化点在哪一侧, 就把哪一侧抽成接口;
- 原则: 组合优于继承, 依赖抽象而不是具体实现;
- 判断: 没有第二个实现时先不抽象, 等变化出现再重构;

```ts
type Handler = (payload: unknown) => void;

class EventBus {
  private map = new Map<string, Set<Handler>>();

  on(topic: string, fn: Handler) {
    if (!this.map.has(topic)) this.map.set(topic, new Set());
    this.map.get(topic)!.add(fn);
  }

  off(topic: string, fn: Handler) {
    this.map.get(topic)?.delete(fn);
  }

  emit(topic: string, payload: unknown) {
    for (const fn of [...(this.map.get(topic) ?? [])]) fn(payload);
  }
}
```

## 发布订阅的原理是什么？

- 角色: 发布者、订阅中心、订阅者三方, 发布者不认识订阅者;
- 存储: 用 `topic → 订阅者集合` 的映射登记关系;
- 发布: 按主题取出集合, 逐个调用回调;
- 退订: 从集合移除, 否则回调一直被持有;
- 遍历: 先复制集合再调用, 避免回调中增删导致漏发;
- 一对多: 一个主题可以有任意多个订阅者, 天然广播;

## 和观察者模式有什么区别？

- 观察者: 目标保存观察者列表并直接通知, 双方相互知道;
- 发布订阅: 多了订阅中心, 发布者与订阅者互不知晓;
- 关系: 发布订阅是在观察者之上加了一层中介;
- 收益: 可以跨模块、跨进程, 也可以换成真正的消息中间件;
- 代价: 多一次转发, 调用链更难追踪;

## 工程上要注意什么？

- 泄漏: 组件卸载必须 `off`, 长期存活的 bus 会持有闭包;
- 顺序: 同步 emit 按注册顺序执行, 异步投递则不保证;
- 背压: 消费者慢时同步总线会阻塞发布者, 需要队列与限流;
- 错误: 一个回调抛错会中断后续回调, 要逐个 try/catch;
- 分布式: Kafka 等中间件把订阅中心独立出来, 换取持久化与重放;
