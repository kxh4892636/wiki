# HTTP/1.0、1.1、2.0 有哪些主要区别？

## 常见问题

- 简述 HTTP 1.0，1.1，2.0 的主要区别

## 概念索引

- 持久连接: 一条 TCP 连接上跑多个请求;
- Host: 首部里声明目标虚拟主机;
- 管线化: 连发多个请求, 响应仍按序返回;
- 队首阻塞: 前面的响应慢, 后面的全被堵住;
- 二进制分帧: 把报文拆成带 stream id 的帧;
- 多路复用: 一条连接上交错传输多个流;
- HPACK: 用静态表与动态表压缩首部;
- QUIC: 跑在 UDP 上的可靠传输, 与 HTTP/2 的分帧思路同源但换掉了 TCP;

## 三个版本各自解决了什么？

| 版本 | 传输 | 连接复用 | 主要改进 |
| --- | --- | --- | --- |
| HTTP/1.0 | TCP | 一次请求一条连接 | 确立请求/响应模型 |
| HTTP/1.1 | TCP | 默认持久连接 | Host、分块传输、范围请求、缓存增强 |
| HTTP/2 | TCP + TLS | 单连接多路复用 | 二进制分帧、HPACK、流优先级 |
| HTTP/3 | UDP + QUIC | 单连接多路复用 | 消除 TCP 层队首阻塞、0-RTT、连接迁移 |

- 版本号只描述报文与连接的组织方式, 方法、状态码、语义基本不变;
- 越靠后的版本, 越依赖「一条连接上跑多个流」这个前提;

## HTTP/1.0 到 1.1 改了什么？

- 持久连接: 默认复用连接, 省掉重复握手与慢启动;
- 虚拟主机: 必须带 `Host`, 一个 IP 承载多个站点;
- 分块传输: `Transfer-Encoding: chunked`, 长度未知也能边生成边发;
- 范围请求: `Range` 加 `206`, 支持断点续传与视频拖动;
- 缓存增强: 引入 `ETag` 与 `Cache-Control`, 从绝对时间改成相对策略;
- 管线化: 可以连发请求, 但响应必须按序, 实际很少开启;

## HTTP/1.1 的队首阻塞从哪来？

- HTTP 层: 管线化要求响应按请求顺序返回, 前一个慢就堵住后一个;
- 浏览器绕法: 同域名开 6 条左右连接, 用并发掩盖排队;
- TCP 层: 丢一个包, 后面所有字节都得等重传;
- 代价: 并发连接多, 握手、TLS 与慢启动开销被放大;

## HTTP/2 如何做到一条连接并发？

```text
一条连接
├─ stream 1: HEADERS ── DATA ── DATA
├─ stream 3: HEADERS ── DATA
└─ stream 5: HEADERS ── DATA ── DATA
帧头里带 stream id, 接收方按 id 把帧拼回各自的消息
```

- 分帧: 报文拆成 `HEADERS`、`DATA` 等二进制帧, 帧可交错发送;
- 多路复用: 多个流共享一条连接, 请求不再等前一个响应;
- 首部压缩: 静态表给常见首部编号, 动态表缓存本连接用过的首部;
- 流优先级: 客户端声明谁先发, 服务端参考调度;
- 服务端推送: 本意是省往返, [Chrome 106 起移除](https://developer.chrome.com/blog/removing-push), Firefox 132 起默认关闭;

## HTTP/2 还剩什么问题，HTTP/3 怎么解？

| 问题 | 原因 | HTTP/3 的做法 |
| --- | --- | --- |
| TCP 层队首阻塞 | 一个包丢了, 所有流一起等 | QUIC 在用户态按流重组, 只影响该流 |
| 建连慢 | TCP 与 TLS 握手串行 | QUIC 合并传输与 TLS 1.3, 1-RTT, 复访 0-RTT |
| 换网断连 | 连接由四元组标识 | 用连接 id 标识, Wi-Fi 切 4G 不断 |
| 中间设备僵化 | TCP 选项被沿途设备丢弃 | 传输层全加密, 设备只能转发 |

## 升级与兼容要注意什么？

- 协商: 客户端用 `Upgrade` 首部或 TLS 的 ALPN 选择 `h2`;
- 明文: `h2c` 用得少, 公网基本是 TLS 上的 `h2`;
- 回退: 服务端要能同时提供 1.1, 老客户端仍需可用;
- 成本: 2.0 对 1.1 语义兼容, 应用代码基本不改, 改的是网关与链路;
