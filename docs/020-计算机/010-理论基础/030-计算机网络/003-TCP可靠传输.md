# TCP 如何保证可靠传输与数据有序？

## 常见问题

- TCP 怎么保证可靠传输？
- 简述 TCP 滑动窗口以及重传机制
- 简述 TCP 协议的延迟 ACK 和累计应答
- 如何解决 TCP 传输丢包问题？
- TCP 如何实现数据有序性？

## 概念索引

- 检验和: 检测报文段损坏;
- 序号与确认: 按字节编号，累计确认;
- 重传: 超时重传与快速重传;
- 滑动窗口: 控制发送与接收节奏;
- 延迟 ACK: 推迟确认，减少 ACK 数量;
- 有序性: 序号排序、去重、缓存失序段;

## TCP 保证可靠传输的机制有哪些？

| 机制 | 作用 |
| --- | --- |
| 检验和 | 发现首部与数据损坏 |
| 序号 | 给每个字节编号，识别丢失与重复 |
| 确认号 | 累计确认已连续收到的字节 |
| 超时重传 | 定时器到期未确认则重发 |
| 快速重传 | 3 个冗余 ACK 立即重发 |
| 滑动窗口 | 限制在途未确认数据量 |
| 流量控制 | 按接收方 rwnd 调整发送 |
| 拥塞控制 | 按网络状况调整 cwnd |
| 连接管理 | 握手同步序号，挥手可靠关闭 |

## 滑动窗口如何工作？

```text
发送窗口:
[ 已发送已确认 ][ 已发送未确认 ][ 可发送未发送 ][ 不可发送 ]
                <-- 窗口大小 -->
```

- 窗口左沿: 最早未被确认的字节;
- 窗口右沿: 最早不能被发送的字节;
- 发送约束: 在途未确认字节数 ≤ min(rwnd, cwnd);
- 接收窗口 rwnd: 接收缓存剩余空间，防止接收方溢出;
- 窗口扩大选项: 把 16 位窗口字段放大，支持高带宽时延积;

## 重传机制如何工作？

| 机制 | 触发 | 特点 |
| --- | --- | --- |
| 超时重传 | RTO 到期 | 保守，可能等待较久 |
| 快速重传 | 收到 3 个冗余 ACK | 不等超时，提前重发 |
| SACK | 接收方告知已收到的区间 | 只重传缺失段，减少浪费 |

```text
RTO = EstimatedRTT + 4 × DevRTT
超时后 RTO 加倍，避免拥塞时反复重传
```

- 冗余 ACK: 收到失序段时，重复发送期望序号的 ACK;
- 快速重传: 3 个冗余 ACK 说明中间段大概率丢失;
- SACK: 选择确认，告诉发送方哪些区间已收到;
- 重传次数过多仍失败时，连接最终会被重置;

## 延迟 ACK 与累计应答是什么？

- 累计应答: ACK=n 表示 n 之前的所有字节都已收到;
- 延迟 ACK: 接收方不立即回 ACK，等待一小段时间或收到两个报文段再回;
- 目的: 减少 ACK 数量，降低开销;
- 代价: 增加发送方等待，可能拖慢重传判断;
- 与 Nagle 同用: 小包与延迟 ACK 可能互相等待，增加延迟;
- 调整: 对延迟敏感的业务关闭 Nagle（TCP_NODELAY）;

| 场景 | 行为 |
| --- | --- |
| 连续收到两个满 MSS 段 | 立即 ACK |
| 只收到一个小段 | 延迟最多约 200ms 再 ACK |
| 收到失序段 | 立即发送冗余 ACK |
| ACK 丢失 | 发送方超时重传，接收方再次 ACK |

## 数据有序性如何实现？

```text
发送: seq=1000, 2000, 3000
接收: 1000 到, 3000 先到, 2000 丢失
缓存: 3000 暂存
重传: 2000 到达
交付: 1000 → 2000 → 3000 按序交给应用
```

- 每个字节有唯一序号;
- 接收方按序号排序，失序段先缓存;
- 重复段直接丢弃;
- 只有连续到某个序号，才把数据交付应用并推进 ACK;
- 应用看到的是有序字节流，不需要自己排序;

## 丢包如何处理？

| 层面 | 手段 |
| --- | --- |
| TCP | 快速重传、超时重传、SACK、拥塞控制 |
| 链路 | FEC、重传、链路冗余 |
| 应用 | 超时重试、幂等、请求去重 |
| 观测 | 重传率、RTT、丢包率、tcpdump |

- 先判断丢包类型: 随机丢包、拥塞丢包、链路故障;
- 拥塞丢包: 降低发送速率，避免越丢越重传;
- 无线随机丢包: 适当容忍，避免误判拥塞;
- 应用重试要配幂等键，防止重复写入;
