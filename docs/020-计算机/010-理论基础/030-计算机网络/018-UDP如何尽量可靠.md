# 从系统层面看，UDP 如何做到尽量可靠？

## 常见问题

- 从系统层面上，UDP 如何保证尽量可靠？

## 概念索引

- 不可靠: 不保证到达、顺序与不重复;
- 校验和: 只能发现位错误, 发现后直接丢包;
- 应用层协议: 可靠性由使用 UDP 的程序自己补;
- 序号与确认: 判断丢了什么、收齐了什么;
- 重传: 超时或冗余确认触发补发;
- FEC: 用冗余包换更低的恢复延迟;
- 拥塞控制: 自己退让, 避免把网络打崩, 与重传一起构成「尽量可靠」;

## UDP 本身能保证什么？

- 端口: 能定位到进程, 实现多路分解;
- 校验和: 覆盖伪首部与数据, 出错就丢包, 不重传;
- 边界: 保留报文边界, 一次收发一条;
- 不保证: 到达、顺序、不重复、不拥塞控制;
- 结论: 可靠性只能由应用层协议补, 内核不替你做;

## 应用层怎么补可靠？

```text
发送: 分配序号 → 存入发送缓冲 → 发出 → 启动定时器
接收: 校验序号 → 放入重组缓冲 → 回 ACK → 按序交付
超时: 重传该序号并指数退避, 连续重复 ACK 可提前重传
```

- 序号: 给每个报文编号, 用于去重、排序与确认;
- 确认: 回 ACK 或 ACK 位图, 告诉对端收到哪些;
- 重传: 超时重传, 配合快速重传降低延迟;
- 缓冲: 乱序先存, 收齐再交付;
- 去重: 重复包按序号丢弃, 避免业务重复执行;

## 前向纠错怎么帮忙？

```text
发 4 个数据包 D1 到 D4, 再发 1 个校验包 P, P 为四者异或
丢了 D2 时: D2 = P 异或 D1 异或 D3 异或 D4, 不用重传
丢两个及以上: 仍然要重传
```

- 思路: 多发冗余包, 丢一个能在本地还原;
- 收益: 少一次往返, 适合实时音视频;
- 代价: 用带宽换延迟, 丢包多时浪费明显;
- 组合: FEC 兜底常见丢包, 重传兜底剩余丢包;

## 拥塞控制为什么也要自己做？

- 无退让: UDP 没有拥塞控制, 猛发会把别人挤掉;
- 做法: 估算带宽与 RTT, 按窗口或令牌桶限速;
- 信号: 丢包、延迟上升、ECN 标记都可当拥塞信号;
- 起步: 慢启动式增长, 丢包后减半, 与 TCP 类似;
- 实现: QUIC、KCP、SRT 各自实现了这一套;

## 系统层还能做哪些调优？

| 手段 | 作用 |
| --- | --- |
| 调大 `SO_RCVBUF` | 减少收包时因缓冲满而丢 |
| 批量收发 | 用 `recvmmsg`、`sendmmsg` 降 syscall 开销 |
| GSO 与 GRO | 内核聚合报文, 提高吞吐 |
| 多队列与 `SO_REUSEPORT` | 多线程并行收包 |
| ECN | 用显式拥塞通知代替丢包信号 |

- 边界: 系统层只能减少本机丢包, 网络丢包仍靠应用层协议;
- 别自造: 直接用 QUIC 或成熟库, 比手写可靠层省事少坑;
