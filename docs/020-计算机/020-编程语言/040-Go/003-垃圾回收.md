# Go 的垃圾回收机制是什么？

## 常见问题

- 简述 Golang 垃圾回收的机制
- 两次 GC 周期重叠会引发什么问题，GC 触发机制是什么样的？

## 概念索引

- 三色标记: 白、灰、黑表示对象是否可达;
- 写屏障: 并发标记时维护对象引用关系;
- 并发标记清除: 标记与用户程序并发执行;
- STW: stop the world，暂停用户 goroutine;
- 触发: 堆增长、内存上限或手动调用;
- 逃逸分析: 编译器决定变量放栈还是堆;
- 辅助 GC: 分配快的 goroutine 自己还标记债;

## Go 的内存机制是什么？

| 层 | 内容 | 谁管 |
| --- | --- | --- |
| 栈 | 每个 goroutine 私有，放局部变量 | 按需增长 |
| GC 堆 | 对象住的地方，GC 扫描的范围 | mallocgc |
| 进程内存 | 堆 + 栈 + 二进制 + runtime 元数据 | 内核 |

```go
func f() *int { x := 1; return &x } // 地址外泄，逃逸到堆
func g() int  { x := 1; return x }  // 只用值，留在栈
```

## 一次 GC 经历哪些阶段？

| 阶段 | 是否 STW | 做什么 |
| --- | --- | --- |
| 标记准备 | 短暂 STW | 开启写屏障，初始化标记任务 |
| 并发标记 | 并发 | 从根对象出发标记可达对象 |
| 标记终止 | 短暂 STW | 关闭写屏障，完成剩余标记 |
| 并发清除 | 并发 | 回收白色对象，归还内存 |

- 根对象: 栈、全局变量、寄存器等可达起点;
- 灰色: 已发现但还没扫描完的对象;
- 黑色: 已扫描完的对象;
- 白色: 标记结束后仍不可达，等待回收;

## 写屏障解决什么问题？

- 场景: 并发标记时用户程序仍在改指针;
- 风险: 黑对象指向白对象，白对象漏标被误回收;
- 写屏障: 每次写指针时插一段钩子，把变化告诉 GC;

## 为什么需要辅助 GC？

- 场景: GC 标记时，程序照常申请内存;
- 矛盾: 后台标记线程少，追不上所有 goroutine 的分配速度;
- 办法: 分配多的 goroutine 去扫灰队列里排队的对象;
    - 分清: 自己新分配的对象直接标黑，不用扫;
- 代价: 分配猛的线程被拖慢，这是有意踩的刹车;

## GC 由什么触发？

| 触发方式 | 说明 |
| --- | --- |
| 堆增长 | 达到 GOGC 计算的目标堆大小 |
| 内存上限 | 接近 GOMEMLIMIT 时更积极回收 |
| 手动 | runtime.GC() 强制一次 |
| 定时兜底 | 长时间未 GC 时由后台触发 |

```go
import "runtime/debug"

debug.SetGCPercent(100)          // 默认：堆增长 100% 触发
debug.SetMemoryLimit(512 << 20)  // 软内存上限 512MB
```

- GOGC=100 表示下次目标约为当前存活堆的 2 倍;
- GOGC=off 关闭基于堆比例的触发，但仍受内存上限约束;
- 内存上限是软限制，不保证绝不超限;

## 两次 GC 周期会重叠吗？

- Go runtime 同一时间只运行一个 GC 周期;
- 上一次标记/清除未结束时，不会并行启动下一次完整 GC;
- 触发过密时会出现“背靠背”GC: 上一轮刚结束就进入下一轮;
- 后果: CPU 被 GC 与辅助标记占用，吞吐下降，延迟抖动;
- 处理: 调大 GOGC、设置 GOMEMLIMIT、减少高频分配、查内存泄漏;

## 如何观察 GC？

```bash
GODEBUG=gctrace=1 ./app
```

- gctrace 输出每轮 GC 的堆大小、目标、STW 时间;
- 关注 GC 频率、堆增长、STW 与辅助标记占比;
- 先用 pprof 找分配热点，再调 GC 参数;
